# 0.2.0 — comparison of the four implementations

Four sea-trade builds exist in this repo. They solve the same task (time-ordered
event queue, ships trading between ports, a clock that can jump) with different
data structures, different economics and different amounts of polish. This file
records what each one does, what was wrong with it, and what the best-of in the
repo root took from where.

## the four

| | `A2026/` | `Beam1/` | `GLM5.3-sea-trade-queue-demo.html` | `GPT6Luna.html` |
|---|---|---|---|---|
| queue | parallel typed arrays, zero allocation per event | objects in a plain array | objects + `seq` FIFO tie-break | objects in a plain array |
| files | `index.html` + `exec_queue.js` `sim.js` `gui.js` `style.css` | `Beam-1.html` + `js/queue.js` `js/main.js` | one file | one file |
| sim | headless, seeded, node-testable | inside `main.js`, `Math.random` | inside the file, `Math.random` | inside the file, `Math.random` |
| ports / goods | 6 / 3 | 5 / 1 | 6 / 5 | 4 / 3 |
| event kinds | dispatch, arrival | arrival, unload, retry | depart, arrive, unload, load, produce, spawn | arrival |
| fleet | 30 slots, retirement + deferred replacement | fixed, no retirement | 26, spawn until the cap | 3, fixed forever |
| economy | production only | none, a conserved total | production, per port | none |
| controls | continuous/jump, ×1–1000, port click | speed slider, fleet slider | speed ×1–1000, add ship | speed ×1–100 |
| readout | HUD stats, queue timeline, port bars | plain text line | stats, upcoming list, event log | clock, log, stock chart |

Only `A2026` is testable without a browser: its sim is a module that runs under
node, the other three are welded to their DOM. That decided the base.

## defects found

`Beam1/`
- `resize()` copies CSS pixels into the backing store, so on a retina display
  the whole map renders at half resolution. Fixed: `devicePixelRatio` backing
  store with a `setTransform(dpr, …)` and drawing in CSS pixels.
- the `nships` slider only updated its own label; the fleet changed only after
  a reset. Fixed: it rebuilds the world on release (`change`).
- `updateUI()` ran `q.toArray().sort()` on every frame, copying and sorting the
  whole heap 60 times a second. Fixed: the readout is throttled to 10 Hz.
- a ship parked at an empty port pushed a retry event every minute, forever.
  Fixed: back off to 5–30 minutes.
- `step()` advanced the clock to the target even when the 5000-event guard cut
  the drain short, leaving events in the past. Fixed: hold the clock at the last
  event, as GLM5.3 already did.

`GLM5.3`
- `push()`/`pop()` swapped with `[h[i], h[p]] = [h[p], h[i]]`, which allocates a
  temp array at every sift level. Fixed: hole sift, which also made this the
  fastest object heap (see the benchmark).
- production clamped stock at 220 while unloading clamped at 260, so a port
  could hold more than the bars could show. Fixed: one `STOCK_MAX`.
- the event log built a DOM row per event at any speed. Fixed: at most one row
  per 90 ms.

`GPT6Luna`
- the log was never trimmed: **158,000 DOM rows after two minutes** at ×100.
  Fixed: keep the last 120 rows.
- `document.querySelector` was called inside the frame loop. Fixed: cached.
- the 10000-event cap advanced the clock past the events it skipped. Fixed:
  hold the clock at the last processed event.

all four
- **no sink for supply**: production ran into `STOCK_MAX` and the bars sat at the
  ceiling (`A2026`'s own measurement: 82.9% average fill, only 0.5% of samples
  with an empty bin). The other three are worse — no production at all, so the
  fleet eventually sails an empty map. This is the single biggest quality gap
  between the builds and is why the best-of adds consumption ticks.

`A2026/style.css`
- the `@media (max-width: 720px)` block re-declared `#timeline`, `.caption`,
  `#qtl`, `#controls` and `button`, a copy-paste of the rules above it.

While converting GLM5.3's sift to the hole form I compared the parent that had
just moved down instead of the event being sifted, and the heap silently lost
ordering. The A/B benchmark asserts drain order, so it failed loudly — worth
keeping that assertion.

## queue benchmark — `node experiments/queue_ab.js`

Same event stream, same node, each queue used the way its own demo uses it
(best of three runs, `experiments/logs/queue-ab.log`):

| workload | A2026 typed arrays | Beam1 | GLM5.3 | GPT6Luna |
|---|---|---|---|---|
| 200k random times, push + drain | **41.2 ms** | 119.1 ms | 138.8 ms | 90.1 ms |
| steady depth 64, 400k clock steps | **32.6 ms** | 53.8 ms | 52.7 ms | 50.4 ms |
| depth 2000, 150 big jumps | **37.2 ms** | 62.6 ms | 65.9 ms | 51.4 ms |

Typed arrays win everywhere by 1.4–3.4x: the object heaps allocate one object
per event and chase pointers. But at the depth these demos actually run (36
events: one arrival per ship plus one tick per port) every queue does
14–25 million operations per second, so the queue was never the frame-rate
bottleneck — the choice buys headroom and a steady GC, not speed.

## verdict

The approaches are the same shape (binary min-heap, event-time handlers); the
data structures and the completeness are not. `A2026` is the only build that
can be tested headlessly, the fastest, and the only one with a retirement loop
that keeps a stable fleet — so it became the base. The best-of adds what the
others were better at and fixes the defect all four shared.
